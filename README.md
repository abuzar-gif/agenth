# AgentH

A local-first Next.js / TypeScript agent workspace. Uses PostgreSQL + Prisma, Auth.js, local-only Ollama + Qwen3 reasoning, explicitly configured ElevenLabs voice, real Playwright Chromium, pg-boss persistent jobs, SSE activity, and explicit approvals for external changes.

## Run on Windows

Node.js 24 is recommended. From this folder:

```powershell
npm ci
npm run setup
npx playwright install chromium
```

`setup` creates `.env` with random secrets only if it does not already exist. It never overwrites an existing environment file. Keep `.env` and `.runtime` private; neither is committed.

In three terminals:

```powershell
# Terminal 1: actual portable PostgreSQL on 127.0.0.1:5432
npm run db:local

# Terminal 2: initialize tables, then start persistent worker
npm run db:push
npm run worker:start

# Terminal 3: production build and server
npm run build
npm run start
```

Open http://localhost:3000 and create your own account. No default account or credentials are included. Development: `npm run dev` instead of build/start. Stop processes with Ctrl+C. The database and schedules remain on disk. Do not run multiple browser workers against the same storage directory. If port 5432 is occupied, configure a different port in DATABASE_URL before starting.

For subsequent local launches, right-click `Start-AgentH.ps1` and choose **Run with PowerShell**, or run `powershell -ExecutionPolicy Bypass -File .\Start-AgentH.ps1`. It starts needed services in hidden windows and saves their logs/PIDs under `.runtime`. It preserves existing services and builds only when no production build exists; after code changes, run `npm run build` while the app is stopped. This launcher does not open a public tunnel. After editing AI environment settings, restart the worker and app to load them.

Alternatively use Docker Desktop: `docker compose up -d postgres`, then db:push, worker and app. Set POSTGRES_PASSWORD in `.env`; it must match DATABASE_URL. Portable PostgreSQL is intended for local development; use a managed PostgreSQL service with TLS and backups for production.

## Local AI setup — no paid API

This build permits only a loopback Ollama endpoint and local Qwen3 models. Cloud endpoints, cloud-tagged models and paid reasoning-provider routing are disabled. ElevenLabs is a separately authorized speech service, configured only on the backend. The browser talks only to the authenticated Next backend.

On this laptop (16 GB RAM, Intel i5-1145G7, Iris Xe), automatic selection recommends `qwen3:4b-instruct` to leave memory for Windows, the database and Chromium. The generic `qwen3:4b` tag resolved to a thinking-only model during setup, so it is excluded from normal automatic chat selection. Runtime discovery uses `/api/tags`; `AI_MODEL=auto` selects an installed suitable Qwen3. The Models setting can select another installed Qwen3 explicitly. Available RAM and CPU load affect actual performance.

The verified portable CPU runtime is under `.runtime/ollama-cpu`. To reproduce it using the official Ollama Windows archive:

```powershell
python scripts/portable-ollama.py --install
$env:OLLAMA_MODELS=(Join-Path $PWD '.runtime/ollama-models')
$env:OLLAMA_NO_CLOUD='1'
.\.runtime\ollama-cpu\ollama.exe serve
# In another terminal:
.\.runtime\ollama-cpu\ollama.exe pull qwen3:4b-instruct
```

Alternatively use `scripts/install-local-ai.ps1` for the signed official Windows installer and automatic model selection. Downloads are real and can take time. Keep the server running on `http://localhost:11434`. No model response is substituted when the service is unavailable.

Environment settings:

```env
AI_PROVIDER=ollama
OLLAMA_URL=http://localhost:11434
AI_MODEL=auto
LOCAL_SPEECH_URL=http://localhost:8001
LOCAL_SPEECH_TOKEN=<random shared local worker secret generated by setup>
```

## Optional local neural voice and local recognition

With the explicit setting `VOICE_PROVIDER=local`, speech stays on this computer. No browser TTS or alternate provider is silently used. Whisper recognition remains local even when ElevenLabs is selected. The local worker runs Meta MMS neural English/Urdu voices and multilingual Whisper-base CPU/int8 recognition. Urdu uses the official `facebook/mms-tts-urd-script_latin` checkpoint; Qwen3 prepares a meaning-preserving Roman Urdu spoken rendition while the visible original transcript is preserved. Model quality is not equivalent to a commercial studio voice and must be judged on the target device. MMS weights are CC-BY-NC 4.0: suitable for this non-commercial school project; obtain appropriate rights or replace the model for commercial use.

```powershell
python -m venv .runtime/speech-venv
.\.runtime\speech-venv\Scripts\python.exe -m pip install -r speech/requirements.txt
.\.runtime\speech-venv\Scripts\python.exe speech/warmup.py
.\.runtime\speech-venv\Scripts\python.exe speech/server.py
# Actual synthesis/recognition verification:
.\.runtime\speech-venv\Scripts\python.exe speech/test_local.py
```

The worker binds only 127.0.0.1:8001 and checks LOCAL_SPEECH_TOKEN for synthesis/recognition. Only the authenticated backend exposes these services to users. First-run model downloads require internet; warmed models run locally. Recorded audio is decoded from real browser recordings, restricted to 90 seconds, and temporary files are deleted. Actual microphone and playback PCM amplitude drives the shared orb through Web Audio. Mute stops recording/playback. iPhone Safari microphone and voice quality require manual device verification.

## Conversations and global orb

`/dashboard/welcome` persists controlled onboarding progress and user-entered answers. Qwen3 generates brief acknowledgments and next questions. A clearly labeled guided question remains available when the local model is unavailable; it is not presented as an AI response. Back, skip, edit chips, review and final confirmation preserve user control.

Dashboard chat provides server-streamed NDJSON replies, conversation creation/rename/search/delete, saved messages, UTF-8 text attachments, cancellation and regeneration. Only recent bounded history is sent to the model; complete transcripts stay in PostgreSQL. Chat has no authority to perform external actions. Use Chief tasks or Browser task mode for tools and approvals.

OrbProvider shares idle/listening/thinking/speaking/working/success/error/paused/muted/offline state. Speaking starts only after actual media playback begins. Listening begins only after microphone capture starts. Task states come from backend events. All major screens use the same original CSS sphere, including auth, welcome, dashboard/sidebar, agents, tasks, browser and settings. Reduced-motion preferences disable decorative motion.

## Authentication and Google apps

- Email/password sign-up and Auth.js JWT sessions work with the local database. Password accounts are explicitly unverified; use Google or SMTP email links when email ownership matters.
- Google sign-in needs AUTH_GOOGLE_ID and AUTH_GOOGLE_SECRET. Add authorized redirect URI `http://localhost:3000/api/auth/callback/google` in Google Cloud Console.
- Gmail, Calendar, and Contacts each use a separate consent flow. Also add `http://localhost:3000/api/connectors/google/callback`.
- Enable Gmail API, Google Calendar API and People API as applicable. Set up the OAuth consent screen and add test users while your app is in testing. Some scopes require Google verification for public use.
- Google sign-in requests identity access; each app requests its own needed scope at connection time. The full Gmail feature set uses gmail.modify, Calendar uses calendar.events, Contacts uses contacts.readonly.
- EMAIL_SERVER is an SMTP connection string; EMAIL_FROM must be authorized by your SMTP provider. Without it, email magic links are clearly disabled.
- OAuth/access/refresh tokens are encrypted with AES-256-GCM. TOKEN_ENCRYPTION_KEY must remain stable. Losing/changing it requires reconnecting integrations.
- Disconnect deletes local credentials; use Google account security settings to revoke the provider grant as well.

References: https://authjs.dev/getting-started/adapters/prisma and https://developers.google.com/identity/protocols/oauth2/web-server

## WhatsApp: supported behavior and limits

**Business:** Create a Meta app and authorized Business phone number. Enter its Phone Number ID and access token in Connected apps. The server verifies the number against Meta before saving credentials. WHATSAPP_GRAPH_VERSION is configurable; use a currently supported Graph API version for your app. Text and supported URL attachments use the official `/{phone-number-id}/messages` endpoint. Replies accept a message ID. Sending requires review of the exact recipient and content. Meta's customer-service window, template, account and recipient restrictions still apply; template messaging is not implemented here.

**Receiving:** Configure public HTTPS webhook `/api/webhooks/whatsapp`, WHATSAPP_WEBHOOK_VERIFY_TOKEN, META_APP_SECRET, and subscribe to message events in Meta. POST signatures are verified. Received messages are deduplicated and stored under the owner of the corresponding connected phone number. History consists of messages actually received by this webhook, not a fabricated full inbox. Search uses those stored messages.

**Personal:** There is no enabled official personal-account automation adapter. Open WhatsApp Web through Browser, run the worker with BROWSER_HEADLESS=false, approve manual takeover, and scan the actual QR in the local Chromium window using Linked devices on your phone. Interact manually. No fake QR, scraped contact API, security bypass or connection-success state is used. This requires a local visible desktop; remote interactive video/input streaming is not implemented. The app does not promise automated personal messages, group creation, participant changes, personal contacts/history, or WhatsApp calling.

**Groups:** Meta offers a separate Groups API with eligibility restrictions. This project has no verified eligible account and does not enable group endpoints or assume access to existing groups. Ask Chief for a supported action; unavailable actions return an error or clarification rather than succeeding falsely.

References: https://developers.facebook.com/documentation/business-messaging/whatsapp/overview and https://developers.facebook.com/documentation/business-messaging/whatsapp/groups

## Execution, teams and approvals

Chief creates a validated JSON plan with named specialists and tool schemas. Permissions are checked for every step, including plans recovered from disk. Specialists run sequentially with shared task context and persisted events. Custom agents are limited to read tools. Tool output references such as `$step:0.messages.0.id` let later tools use actual returned identifiers. Arbitrary code execution and unsupported publishers are not tools.

Before an external mutation, the task stops at waiting_approval with the resolved exact tool arguments. An owner can approve or reject. Schedule creation and direct browser interaction controls also require deliberate user actions. Recurring jobs cannot silently reuse old outgoing-message approvals. Agent cancellation/pause stops future steps; an already-started HTTP/browser action may finish and is logged. Read tools retry once. Mutations never auto-retry after ambiguous failures. A crashed worker marks expired leases failed for explicit review, preserving logs and the execution cursor. Review the remote service before resuming a failed mutation to avoid duplicates.

The worker scans durable schedules every five seconds. Missed recurring occurrences coalesce into one execution after restart. Cron is evaluated in the stored IANA time zone, default Asia/Karachi. The first datetime picker uses the computer's local time zone; saved times show in the profile time zone. Task status and completion logs provide in-app notifications. Push/email notifications are not configured.

## Browser and files

Real contexts are isolated per account, capped at four simultaneous sessions per worker. Every request/redirect/subresource is checked against private/local addresses; service workers are disabled. Local file paths are generated IDs under the owning user's `.runtime` directory. Uploads are limited to 10 MB. Download IDs appear in tool results and are retrieved via `/api/files?id=ID` after authentication. Screenshots are private, real PNGs. Cookies/local storage are encrypted on disk between browser sessions. Session storage and full live page state are not preserved.

For a public multi-user deployment, put browser workers inside a dedicated network/container boundary with egress controls: URL/DNS checks alone do not eliminate DNS rebinding or hostile browser exploits. Do not expose this development worker as an unrestricted public browser service. Use per-user quotas, a distributed rate limiter, malware scanning/object storage and an approved identity policy for production. Current rate limiting is per server process. Current SSE connections reconnect periodically; run behind an SSE-capable proxy. External side effects still rely on human approval and provider policy.

## Share with a teacher for free (not started automatically)

Install Cloudflare Tunnel from https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/ and run:

```powershell
cloudflared tunnel --url http://localhost:3000
```

Only after it prints a real `https://…trycloudflare.com` URL is there a public link. Set APP_URL and AUTH_URL to that URL, restart the app, and add both HTTPS Google OAuth callback URLs described above. For Google OAuth, a stable named tunnel or stable hosting URL is usually easier than changing quick-tunnel URLs. Quick tunnels have limits and do not support SSE; use authenticated polling fallback or a stable named tunnel for live activity. Test the public link from another device before sharing. The local computer, PostgreSQL, app, worker, and tunnel must remain running. Publishing/exposing the app requires your approval; no tunnel has been opened by this build.

Reference: https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/do-more-with-tunnels/trycloudflare/

## Production packaging

`npm run build` emits production Next.js server output. `Dockerfile` builds the web/worker image; use `docker-compose.production.yml` for a self-hosted deployment with persistent PostgreSQL and runtime files. Use HTTPS, stable public URLs and production secrets. The production Compose example uses Linux host networking to reach loopback-only Ollama and speech workers; it is not verified on Docker Desktop here. Run the full app natively on Windows using Start-AgentH.ps1. Web and worker must share runtime storage for browser PNGs/uploads, and share the same token encryption key. Keep the browser worker persistent; serverless function hosting alone cannot run the browser/scheduler. Workers on another host need shared object storage and a remote browser-control transport, which are not provided. No external hosting account or public deployment is configured by default.
